# Профиль нагрузки из статистики N запросов

Промпт для случая, когда у пользователя есть **историческая статистика обращений** (access-лог
nginx/gateway, выгрузка из Prometheus/Grafana/ELK, любой список «эндпоинт → число хитов»)
и он хочет воспроизвести реалистичную смесь запросов, а не выдумывать веса руками.

Вся тяжёлая работа — у команды `profile`: она нормализует пути, считает доли, вытаскивает
реальные ID в переменные и оценивает RPS. Твоя задача — подготовить вход, запустить команду
и довести черновик до рабочего сценария.

## Когда использовать

Маркеры в запросе: «сделай профиль из лога», «возьми нагрузку как на проде», «вот статистика
по эндпоинтам», «повтори реальное распределение запросов», приложен `access.log` / CSV / JSON
с хитами.

## Шаг A. Подготовь вход

Поддерживаются три формата (команда определит сам, но можно задать `--format`):

- **access** — строки access-лога с `"GET /path HTTP/1.1" 200`. Если есть таймстемпы
  `[03/Jul/2026:10:00:00 +0000]` — из них оценится средний RPS (→ `load.maxRps`).
- **csv** — заголовок с колонками `path` (обязательна), `method`, `count`/`hits` (опц.).
  Одна строка = один эндпоинт с числом хитов, либо одна строка = один хит.
- **json** — массив `[{ "method": "GET", "path": "/api/v1/pools", "count": 1994 }, ...]`
  или объект `{ "GET /api/v1/pools": 1994, ... }`.

Если данные в Prometheus/Grafana — попроси пользователя выгрузить top-N по
`sum by (path, method) (rate(http_requests_total[...]))` в CSV/JSON вида выше.

## Шаг B. Запусти профилирование

```
node LOADGEN profile <файл> --base-url <URL> --top 20 --out scenario.json
```
- `--base-url` — адрес цели (можно вписать потом руками в сценарий).
- `--top N` — сколько самых частых эндпоинтов взять (по умолчанию 20).
- `--include-writes` — включить POST/PUT/DELETE. **По умолчанию они отброшены** —
  добавляй флаг только если пользователь ЯВНО хочет писать в систему под нагрузкой.

Что делает команда:
- сегменты-ID в путях (числа, UUID, длинные hex) → плейсхолдеры `{{v..}}`, а реальные
  значения из статистики складываются в `vars` (до 200 на позицию) — нагрузка пойдёт по
  настоящим ID, а разбивка «ВЛИЯНИЕ ПАРАМЕТРОВ» покажет, какие из них тормозят;
- `weight` каждого запроса = доля хитов (в процентах) — смесь повторяет исходную;
- при наличии таймстемпов ставит `load.maxRps` = средний исторический RPS.

## Шаг C. Доведи черновик (это ОБЯЗАТЕЛЬНО, файл — черновик)

Прочитай сгенерированный сценарий и поправь:
1. **baseUrl** — если не задал через `--base-url`.
2. **auth** — в черновике `type: "none"`. Если API требует токен (probe покажет 401) —
   впиши `login`/`bearer` блок.
3. **vars** — где реальных значений не было, стоит заглушка `1`; замени на валидные ID
   или подключи файл (`{"file": "ids.txt"}`).
4. **load** — `maxRps` из лога это СРЕДНЯЯ интенсивность. Для теста «выдержит ли пик»
   убери `maxRps` или подними; для проверки «держит ли обычный трафик» оставь.
   Для высокой нагрузки добавь `workers` (см. параллелизм в основном промпте).
5. Убери из `requests` эндпоинты, которые не воспроизводятся в тесте (одноразовые,
   с невалидными в текущей БД ID).

Затем обычный конвейер: `validate` → `run --smoke` → `run`.

## Пример

Вход `access.log` (4000 строк, смесь пулов/токенов/swap). Команда:
```
node LOADGEN profile access.log --base-url http://localhost:8080 --out profiled.json
```
Результат: 4 GET-эндпоинта с весами 51.5 / 31.9 / 9.8 / 6.8 (как в логе), POST /swap
отброшен, `maxRps` = 10 (из таймстемпов), реальные UUID пулов разложены в `vars`.
После вписывания `auth` сценарий сразу проходит smoke против цели.

## Запрещено

- Запускать профиль с `--include-writes` без явного разрешения пользователя на запись.
- Оставлять заглушки `1` в vars, если известны реальные значения.
- Выдавать черновик за готовый сценарий — всегда прогоняй `validate` и `--smoke`.
